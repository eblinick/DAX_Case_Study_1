DAX optimization case studies

Slow reports are rarely a visual problem. They're usually a model or measure problem. This case study is an example of the kind of work I do when looking to optimize a measure.

Why public datasets

Client models stay private

Companies don't publish their semantic models or data. The measures here are deliberately written the naive way, so the same problems can be shown on public data.

Large, but simple

Public datasets can have hundreds of millions of rows, but they're usually clean star schemas. Enterprise models often have 50+ tables, messy relationships and many more measures.

DAX isn't always the fix

Sometimes a measure can't be optimized any further because the limit is the data model or the report design. Knowing when to stop tuning DAX and change the model instead is part of the job.

Case study 1

Contoso: optimizing a slow Net Sales measure

Business rule: order lines with a quantity above 5 get a 10% discount. The original measure applies the rule with an IF inside SUMX, which forces the engine to evaluate every sales row one at a time. Three rewrites move the rule into filters instead, and all versions are tested on a 10M and a 100M Contoso dataset.

Show the original measure 
Net Sales Slow =
SUMX ( Sales,
    IF ( Sales[Quantity] > 5,
         Sales[Quantity] * Sales[Net Price] * 0.9,

Method

  • Tools: Power BI Desktop, Performance Analyzer and DAX Studio (Server Timings).
  • Each query run with a cleared cache (SE Cache = 0 in every screenshot), so results reflect a cold engine.
  • Every rewrite is checked for both speed and identical results. A faster measure that changes the numbers isn't finished.
  • Timings are single runs on one laptop. Differences under about 10% are treated as noise.
